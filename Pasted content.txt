Telegram Bot Technical Framework

Public User Menu + Admin Configuration

1. Architecture Objective

The bot operates with two distinct access levels:

                    TELEGRAM BOT
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
       PUBLIC USER LAYER       ADMIN LAYER
             │                       │
         /start                    /admin
             │                       │
             ▼                       ▼
       User Main Menu         Admin Dashboard
             │                       │
       Callback Handlers      Admin Callbacks
             │                       │
             ▼                       ▼
      Public Functions       Configuration

All Telegram users can trigger "/start".

Only authorized channel owners/administrators can access configuration functionality.

---

2. Access Control Model

The bot should distinguish at least three identities:

USER
ADMIN
OWNER

Recommended permission hierarchy:

OWNER
  │
  ├── Full configuration access
  ├── Manage admins
  ├── Manage channels
  ├── Manage groups
  ├── Manage forwarding
  ├── Manage filters
  └── Manage bot settings
       │
       ▼
ADMIN
  │
  ├── Configuration access according to permissions
  ├── Manage forwarding
  ├── Manage destinations
  └── Manage filters
       │
       ▼
USER
  │
  ├── /start
  ├── Public menu
  ├── Public callbacks
  └── Public bot functions

Do not assume that a Telegram user who can interact with the bot is an administrator.

Every user should be able to send:

/start

The bot determines the user's access level.

   ▼

   │

   │
   ▼

   ▼

5. Admin Menu

Administrators should have a separate configuration entry point.

Example:

⚙️ Administration

[ 📣 Forwarding ]
[ 🎯 Destinations ]
[ 🔣 Filters ]
[ ✍️ Auto-complete ]
[ 🤖 Custom Bot ]
[ 📊 Event Log ]
[ 👥 Administrators ]
[ ⚙️ Settings ]

The "/admin" command can be used as an explicit entry point.

However, the bot must perform authorization every time, not merely hide the button.

---

6. Critical Security Rule

Never implement authorization as:

if callback_data == "admin:settings":
    show_settings()

Instead:

if callback_data == "admin:settings":
    if not is_authorized_admin(user):
        deny_access()
        return

    show_settings()

The same principle applies to:

- Commands
- Callback queries
- Inline buttons
- Deep links
- Webhooks
- Background actions
- Administrative APIs

Hiding an admin button is not an authorization mechanism.

8. Callback Naming Convention

Use structured callback identifiers.

Recommended format:

<scope>:<action>:<identifier>

Examples:

public:menu
public:help
public:channel:info

admin:menu
admin:forward
admin:destination:add
admin:destination:remove
admin:filter:trigger
admin:filter:block
admin:media
admin:autocomplete
admin:settings

For an individual destination:

admin:destination:view:123
admin:destination:remove:123

This makes callback routing predictable and easier to maintain.

---

9. Public Callback Handlers

Public callbacks do not require administrative authorization.

Example:

public:menu
public:help
public:channel
public:information

Handler:

callback
   │
   ▼
Validate callback
   │
   ▼
Public handler
   │
   ▼
Answer callback
   │
   ▼
Edit/send menu

However, the callback should still validate the expected parameters and originating user/session where relevant.

---

10. Admin Callback Handlers

Every admin callback must perform authorization.

Example:

admin:forward

Processing:

Callback
   │
   ▼
Parse callback
   │
   ▼
Is user authorized?
   │
 ┌─┴──────┐
No        Yes
│          │
▼          ▼
DENY     Handler
│          │
▼          ▼
Log      Execute

Unauthorized users should receive a generic response such as:

⛔ You are not authorized to use this function.

Do not expose internal permission details.

---

11. Channel-Based Authorization

Since the configuration concerns Telegram channels, authorization should preferably be based on actual Telegram channel administrator/owner status, rather than merely maintaining a hard-coded list of Telegram user IDs.

Conceptually:

User
 │
 ▼
Selected Channel
 │
 ▼
Telegram Admin Status
 │
 ├── Owner       → Full access
 │
 ├── Admin       → Config access according to permissions
 │
 └── Member      → No admin access

This prevents a user from retaining administrative access after they have been removed as a channel administrator.

13. Owner vs Administrator

The owner should have a special status.

Example:

OWNER

The owner can:

- Configure the bot.
- Configure forwarding.
- Add/remove destinations.
- Configure filters.
- Configure Auto-complete.
- Configure custom bot.
- Manage administrators.
- Change security settings.

An administrator may receive only selected permissions.

The owner should not be removable through normal admin-management operations.

23. Session State

Some configuration workflows require multiple steps.

Example:

Admin selects:
Add Trigger Word

Bot:
Send the new trigger word.

Admin:
sale

Bot:
Trigger "sale" added.

The bot therefore needs temporary conversation state.

Conceptually:

User Session
│
├── user_id
├── role
├── current_menu
├── current_action
├── selected_channel
├── selected_destination
└── pending_confirmation

State should be scoped to the user and expire after a reasonable period.

---

24. Callback Security

Callback data should not contain secrets.

Bad:

admin:set_api_key:SECRET_VALUE

Better:

admin:settings:api_key

Sensitive values should be handled through secure configuration flows and never exposed in callback identifiers.

Callback IDs should also be validated against the user's authorization and the currently selected resource.

---

25. Anti-Tampering

Never trust:

callback_data
user-submitted IDs
channel IDs
group IDs

Validate all of them server-side.

Example:

User:
admin:destination:remove:999

Server:
    Is user authorized?
    Does destination 999 exist?
    Does destination 999 belong to this configuration?
    Is user allowed to remove it?

Only after all checks pass should the deletion occur.

31. Core Security Principle

The most important rule for this architecture is:

                 BUTTON VISIBILITY
                       ≠
                  AUTHORIZATION

An administrator button can be hidden from normal users, but that does not protect the underlying function.

The actual security boundary must be:

Telegram User
     │
     ▼
Identity
     │
     ▼
Role
     │
     ▼
Permission
     │
     ▼
Resource Authorization
     │
     ▼
Callback Handler
     │
     ▼
Action

Therefore, even if a normal user manually constructs:

admin:forward
admin:settings
admin:destination:remove:123

the server must reject the request unless that Telegram user is authorized for that operation.
